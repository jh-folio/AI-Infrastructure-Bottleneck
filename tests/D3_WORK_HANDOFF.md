# D3 Work 실제 인수 — 0.2.0-d3.1

이 파일의 절차는 사용자가 D3 검증을 요청했을 때 적용한다. D1 성공을 D3 결과로 옮겨 쓰지 않는다. 기준 버전과 필요한 파일을 먼저 확인한다. 기존 D1 DB와 실제 연구 원장은 보존하고 별도 새 연구 폴더를 사용한다.

## 첫 실행: 환경과 합성 경로

5개 skill, plugin/runtime/research_cli.py, plugin/database/research_v1.sql이 있는지 확인한다. runtime guide를 읽고 capabilities를 실행한다. `python -X utf8 -m unittest discover -s tests -p "test_*.py" -v`는 합성 자동 검사다. 선택 pypdf/yfinance가 없으면 의존성 지원 상태를 먼저 남긴다.

## 실제 자료와 연구 흐름

사용자가 지정한 작은 연구 질문과 대상 1–2개, 기준일을 사용한다. 지정이 없으면 먼저 범위를 확인한다. 기존 87개 노드 점수/순위나 특정 회사 결론을 기본값으로 생성하지 않는다.

1. 새 state_dir/init 결과 ID를 기록한다. SEC submissions와 companyfacts, 대상 가격 이력, 공식 IR HTML 또는 PDF를 각각 실제 취득한다. HTTP/status·원문 hash·기간/단위·통화/조정 여부·실패 상태를 기록한다. 한 소스 성공을 전체 성공으로 표시하지 않는다.
2. filings/facts와 질문별 search/packet을 사용한다. 같은 문서의 수요·공급 확장·잔존 제약·대안/반증 문맥을 조회한다. API에 없는 규격·프로젝트/과거 실현·반대 자료는 웹으로 보강한다. PDF 표/차트는 시각 검증한다.
3. 동일 scope에서 실제 검토한 지지·반증 evidence를 등록하고 judgment를 만든다. 구체적인 endpoint가 검토된 경우만 assess한다. 근거 없는 부분은 task/Unknown으로 남기고 예시 점수를 실제 데이터에 넣지 않는다.
4. 실제 제공된 심층 리서치 연결을 수행하거나 그 기능의 부재/접근 실패를 명시한다. report 또는 weekly_brief를 만들고 원문 링크·위치·조건·반증·다음 관측이 요약까지 보존되는지 확인한다.
5. audit와 backup을 실행한다. 다음 인계에 state_dir/project_id, 버전, snapshot_id, 주요 record/document IDs, 최신 backup 위치·SHA, 실패/보류/다음 행동을 기록한다. 자료/연구 상태 ZIP은 별도 사용자 결과물이며 GitHub에 올리지 않는다.

## 새 세션

자동 접근 여부를 보려면 먼저 재업로드/초기화 없이 기존 경로를 읽는다. 실제 환경이 유지되지 않았다면 그 실패를 기록하고 검증된 backup으로 새 폴더에 복구한다. 같은 ID·원문 hash·판단/보고서 snapshot을 확인한다. 별도 명시한 테스트 쓰기를 1회 수행하고 같은 request_id 재시도가 inserted=false인지 확인한다. 백업에서 수동 복구된 성공과 자동 재접근 성공은 별개다.

## 사용자 판단 지점

같은 연구 질문의 기존 웹 중심 결과와 비교한다: 새로 확인한 독립 원출처/반증/과거 계획 실현, 판단이 바뀐 구체 근거, 원문 재조회와 요약의 문맥 보존, 미확인의 정확한 범위. 자료 수나 테스트 수만으로 더 깊은 연구라고 판정하지 않는다. D3 실제 자료·심층 리서치 연결·보고서 품질과 새 세션 재접근을 판단한 뒤 D4 반복 추적·D5 화면으로 간다. 자동 예약·장기 지속성·다른 사용자 설치는 여기서 합격 처리하지 않는다.
