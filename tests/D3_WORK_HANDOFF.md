# D3 Work 실제 인수 — 0.2.0-d3.4

[공통 제품 계약](../plugin/methodology/PRODUCT_CONTRACT.md)을 먼저 적용한다. 이 시험은 AI 인프라 공급망의 **병목 위치·심화도·추세를 파악하고 이해하기 쉽게 보여주는 능력**을 검증한다. 특정 기업의 재무 분석이나 자료원 연결 확인만으로 합격하지 않는다. 아래 질문·범위는 D3 검증용 과제이며 모든 사용자의 연구 기본값이나 병목 결론이 아니다. 사용자가 다른 시험 범위를 지정하면 그 지시를 우선한다.

## 기본 시험 질문

> 2026-09-14 기준, AI 인프라 구축과 실제 가동을 제약하는 공급망 병목은 어디에 있는가? 각 병목은 얼마나 심각하고 어떤 제품·지역·프로젝트에 영향을 주는가? 지난 12개월 동안 어디가 심화·완화되거나 새 제약으로 떠올랐으며, 향후 12–24개월에는 어떤 조건에서 달라질 수 있는가? 이를 공급망 흐름에 따라 쉽게 설명하고, 다음에 추적해야 할 지표와 판단 변경 조건을 정리하라.

D3 검증을 요청받고 별도 주제가 없으면 이 과제를 바로 사용한다. 사용자가 임의의 기업 질문·종목을 다시 고르게 하지 않는다. 기준일/기간은 재현 가능한 이번 시험 조건이다. 이후 일반 연구의 기본 날짜로 고정하지 않는다. 투자 매력도·주가·기업 순위는 이번 핵심 질문에 포함하지 않는다.

## 첫 실행: 환경 확인과 보존

실제 실행할 패키지의 manifest/파일 위치/commit을 확인한다. 원격 main 버전 확인만으로 설치본이 갱신됐다고 하지 않는다. [실행 계약](../plugin/workflows/RUNTIME_GUIDE.md)을 읽고 5개 skill, research_cli.py, research_v1.sql을 확인한다. capabilities와 합성 자동 검사는 사전 점검이며 연구 완료가 아니다. 합성 검사 수와 결과는 실제 실행 로그를 따른다. 이미 같은 코드에서 확인한 검사를 문서 변경만으로 반복 요구하지 않는다.

기존 D1 DB와 실제 연구 원장은 보존한다. 처음이면 별도 새 state_dir/init을 사용하고 이미 D3 상태가 있으면 ID·버전을 확인해 재개한다. yfinance 부재 시 선택 의존성 설치 가능 여부를 확인한다. SEC 식별 설정이 없으면 그 경로를 configuration_required로 남기고 공식 IR·공개자료·웹으로 독립적으로 가능한 연구를 진행한다. 필요한 실제 연락처를 만들어내지 않는다. 가격 경로는 부가 기술 검사이며 가격 취득 성공/실패가 물리적 병목 판단을 대신하거나 막지 않는다.

실제 환경의 심층 리서치 skill/tool을 발견해 직접 수행 또는 실제 도구 실행과 결과 접근을 확인한다. 과거 runtime의 `host tool required` 문자열은 별도 API의 필수 조건이 아니다. 없는 도구·작업 ID를 만들지 않는다. 연결이 불가능하면 인계 자료와 해당 한계를 보존하고 가능한 연구를 계속한다.

## 1. 공급망 범위 탐색과 심층 대상 선정

[기존 ID 정체성 목록](../plugin/ontology/node_ids_v1.json)을 참고하여 compute/메모리/제조·패키징, 네트워크·광연결, 데이터센터 냉각·현장설비, 발전·송배전·전력 인입, 소재·공정 투입재, 건설·인력 등 공급망 구간을 먼저 살핀다. 분류는 탐색 범위를 확인하기 위한 것이며 모든 구간을 병목으로 지정하는 목록이 아니다.

구간별로 검토한 원출처, 후보 제약, 여유/정상 완료·완화 신호, 미검토 범위를 기록한다. 유명한 후보나 과거 보고서의 결론만 선택하지 않는다. 87개 ID가 있다는 이유로 87개 모두 조사됐다고 하지 않는다. 기업은 공급자·고객·운영자·프로젝트의 근거로 다루며 회사 전체가 자동으로 평가 단위가 되지 않는다.

광역 탐색 결과에서 실제 가동 영향, 수요 대비 가용 공급 부족, 변화 신호, 다른 구간과의 관계를 근거로 심층 대상을 선정하고 선정·제외 이유를 밝힌다. 확정 병목 수나 순위를 미리 정하지 않는다. 강화 가설뿐 아니라 완화·정상 완료·대체 경로도 조사한다. 서로 다른 범위는 각각 node/제품·규격/지역/기간으로 분리한다.

## 2. 위치·심화도·추세를 설명할 근거 구축

- 각 대상에 수요, 실제 사용 가능한 공급, 공급 증가 후 미충족, 운영 일정 영향, 반증/대체 경로의 다섯 질문을 적용한다. capacity 증설만으로 완화라고 하지 않는다.
- SEC/공식 IR/공개 원문을 코드로 취득·저장하고 filings/facts/search/read-document/packet으로 기간·단위·앞뒤 문맥을 확인한다. 기업 공시 밖의 규격별·프로젝트별·비미국 자료는 공식 원출처 탐색과 웹 교차검증으로 보강한다. 연결하기 쉬운 자료원 때문에 조사 대상을 바꾸지 않는다.
- 원문 공개일·관측기간이 다른 자료에서 과거 계획→수정→현재 실현을 복원한다. 수요도 함께 비교한다. 적어도 비교 가능한 두 시점의 근거가 있어야 추세를 판정하고, 없으면 현재 제약 판단과 추세 미확인을 분리한다. 현재 수치나 최신 수정 vintage로 과거 점수를 만들어 넣지 않는다.
- 각 대상의 심화도는 현재 부족의 강도, 지속성, 다른 운영에 미치는 중요성으로 설명한다. 현행 Scoring 3.1의 적격 입력만 중앙 계산에 넘긴다. 숫자가 부족해도 직접 정성 근거로 가능한 범위한정 판단은 제시하고, 미식별 부분은 Unknown으로 남긴다. 별도 임의 총점/rubric은 만들지 않는다.
- 심화/완화/변화 불명 판단에는 비교 범위·시점·지지/반증·확신도와 이유를 붙인다. 병목의 이동/전파는 기존 제약 완화와 새 구간 제약·연결된 일정 영향이 확인되는 범위에서만 주장한다. 지도상의 기술적 연결만으로 실제 전파를 인정하지 않는다.
- 미래는 외부 계획/전망과 자체 조건부 시나리오를 나누고 수요·ramp·인증·현장·대체 조건과 판단 변경 근거를 밝힌다. 과거 추세를 그대로 연장하지 않는다.

검토한 원문/주장은 adopt, 판단은 judgment, 계획/실현은 event, 미확인은 task로 저장한다. 채택하지 않은 근거의 이유와 다음 관측도 남긴다. 실제 심층 리서치에 이 범위·규칙·원문 위치·지지/반증·공백을 인계하고 결과를 같은 절차로 재검토한다.

## 3. 사용자가 읽고 이해할 결과

결과의 첫 화면/문서는 다음 순서로 작성한다. 기술 검사 로그를 본문 앞에 나열하지 않는다.

1. **한 페이지 핵심 요약:** 지금 어디가 막히는지, 무엇이 심화/완화되는지, 확실한 판단과 아직 구분할 수 없는 부분을 평이한 말로 설명한다.
2. **공급망 위치별 비교표:** 구간/평가 범위, 제약의 강도·지속성·가동 영향, 과거→현재 변화, 확신도, 핵심 근거, 다음 관측을 한눈에 보여준다. 다른 scope를 하나의 글로벌 확정 순위로 합치지 않는다.
3. **핵심 후보별 심층 설명:** 수요와 가용 공급의 관계, 계획→실현 이력, 경쟁 가설·반증, 산업 전반/특정 제품·지역에 적용되는 범위, 미래 조건을 설명한다. 결론의 조건을 표와 요약에서도 유지한다.
4. **추적 목록:** 무엇을 어느 원출처에서 다음에 확인하며, 어떤 관측이면 판단이 유지/강화/완화/기각되는지 적는다. 아직 자동 예약이 실행되는 것은 아니다.
5. **근거 색인과 한계:** 저장된 원문·위치·hash/record/snapshot으로 재조회 가능하게 하고 미검토 구간·수집 실패·점수 비적격·상반된 근거를 밝힌다.

검토한 judgment의 bottleneck/comparison과 분야 간 synthesis_claims를 작성하고 runtime guide의 synthesize를 사용한다. 핵심 요약·위치 비교·범위 공백·이전→현재 판단·추적 항목·인용이 같은 snapshot에서 생성되는지 확인하고 export-report한다. 현재 판단이 여러 개면 종합 결론에 실제 판단 ID와 비교 이유·한계를 연결한다. 이것은 검토 입력을 정리하는 기능이며 자동 원출처 해석이나 D5 화면 구현이 아니다. 렌더링된 요약이 원래 조건·반증을 보존하는지도 실제 Work에서 확인한다.

## 4. 갱신과 새 세션

첫 보고서와 snapshot을 고정하고, 후속 synthesize에는 previous_report_id를 전달한다. 그 뒤, 선택 대상의 후속 근거나 정정을 반영해 수동 변경 요약을 만든다. 이전 판단→추가 근거→유지/수정/미확인 이유→다음 관측이 연결되어야 한다. 같은 기준일 자료를 뒤늦게 추가한 것은 자료 회복이고 실제 산업 변화가 아니다. 실제 새 관측이 없으면 꾸며내지 말고 추세는 위 과거 이력 비교로 검증하며 향후 실시간 갱신은 미검증으로 남긴다.

audit와 최신 backup을 실행하고 state_dir/project_id/버전/snapshot/주요 record/document IDs/백업 SHA/남은 행동을 인계한다. 개인 DB·원문·보고서는 GitHub에 올리지 않는다. 새 세션에서 재업로드/초기화 없이 먼저 재접근을 시도하고, 실패 시 실패 사실을 기록한 뒤 검증된 backup을 새 폴더로 복구한다. 동일 요청 재시도는 중복 생성이 없어야 한다. 수동 복구 성공과 자동 재접근 성공은 구분한다.

## 사용자 판단과 개선 기록

다음은 점수가 아니라 제품 인수 질문이다. 항목마다 실제 근거/산출물과 미충족·개선 필요를 기록한다.

| 평가할 능력 | 확인할 결과 |
|---|---|
| 위치 발견 | 익숙한 기업/후보만 되풀이하지 않고 공급망 검토 범위와 주요 제약 위치를 설명하는가 |
| 심화도 판단 | 수요 대비 부족·지속성·가동 영향을 구분하고 근거보다 강한 점수/순위를 만들지 않는가 |
| 추세 추적 | 비교 가능한 두 시점과 실제 실현을 연결하며 자료 회복/방법 변경을 산업 변화와 구별하는가 |
| 넓이와 깊이 | 탐색 범위를 밝히고 결정에 중요한 후보의 독립 근거·반증·과거 이력까지 확인했는가 |
| 이해하기 쉬운 전달 | 사용자가 요약과 비교표만 읽어도 어디가 왜 막히고 무엇을 다음에 볼지 알 수 있는가 |
| 재현·연속성 | 요약에서 원문으로 돌아가고 다음 실행에서 같은 판단/상태를 이어갈 수 있는가 |

동일 범위·기준일의 기존 웹 중심 결과가 있을 때만 비교하고, 없으면 비교 기준선 부재를 명시한다. 자료 수/테스트 수만으로 더 넓고 깊다고 판정하지 않는다. 기준선 조사를 별도 수행하지 않았다면 실행한 것처럼 쓰지 않는다. 결함은 자료 취득·탐색 범위·판단·보고서 전달·상태 갱신 중 어느 단계 문제인지 분류하고 재현 입력/예상 결과와 함께 남긴다. D3 Work 인수·독립 해석 검토·baseline 승인·D4 예약·D5 화면·D6 외부 설치는 각각 구분한다.

## D3.4 추가 인수: 의미 검토·문체·실제 심층 리서치

새 패키지는 0.2.0-d3.4다. 이전 보고서는 보존하고 새 request_id로 정정한다. RUNTIME_GUIDE의 judgment_reviews, research_execution, comparison_scope를 작성한다. 이번 재시험은 새 연구 질문을 사용자에게 요구하지 않고 기존 공급망 목적과 보존 상태를 이어간다.

1. 기존 Work 실행 기록에서 실제 심층 리서치 스킬/도구 적용과 반환 결과를 찾는다. 있으면 실제 증거와 결과를 별도 저장하여 참조한다. 없으면 unknown/not_run을 구분하고, 현재 환경에서 실제 스킬을 발견해 그 지침으로 수행한다. 일반 웹 조사·synthesize를 수행 기록으로 대신하지 않는다.
2. 발전원 접속→부하 인입, 전망→관측, 증설→수요 충족·완화의 잘못된 전용을 재검토한다. 비교에 중요한 반도체 구간이 비어 있으면 그 비교를 유보하거나 보강한다. source_fit의 분류를 통과시키려고 원문 모집단을 평가 대상과 같게 고쳐 쓰지 않는다.
3. 본문은 내부 코드 없이 문장으로 읽히는지, 전문 용어를 설명하는지, 출처·범위·반증이 남는지 확인한다. 부록에 검증 식별자와 실행 근거를 둔다. 판단 정정과 실제 산업 변화를 구분한다.
4. 결과 보고서와 실제 실행 기록·반환 결과·audit/재접근 확인을 함께 보존한다. 실행 증거가 없으면 심층 리서치 완료나 D3 전체 인수로 표시하지 않는다.
