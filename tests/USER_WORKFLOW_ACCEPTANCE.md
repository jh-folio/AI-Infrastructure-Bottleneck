# 실제 사용자 흐름 확인

이 문서는 작성자 코드 검사와 분리된 실제 호스트/사용자 확인 과제다. 설치본 README만 제공받은 사용자가 기능 이름·CLI를 배우지 않고 아래 요청으로 진행할 수 있는지 확인한다. 합성 자동 테스트 통과를 이 과제의 성공으로 기록하지 않는다.

1. 설치 가능한 출처에서 AI Bottleneck을 설치/갱신하고 새 Work 대화를 시작한다. 실제 manifest 버전과 5개 스킬 가용성을 확인한다. 설치 경로·계정 접근 제약과 사용자 수동 조작이 있었는지 기록한다.
2. “무엇을 할 수 있어?”: 짧은 기능·순서·요청 예시를 제공하고 DB 생성/긴 연구를 시작하지 않아야 한다.
3. “처음 시작해줘”: 기존 상태가 있으면 보존하고, 없으면 실제 지원 저장 위치에서 설정부터 조사·검토·보고서/화면까지 이어가야 한다. 첫 연구는 현행 전수 조사·완료 계약을 충족해야 하며 기능 시험으로 축소하지 않는다.
4. “저장된 보고서와 지도를 보여줘”, “이 판단의 근거를 설명해줘”: 같은 report/snapshot의 결과와 원문을 제공하고 새 전체 조사를 시작하지 않아야 한다. 결과가 없으면 없다고 설명하고 시작/재개 방법을 제시해야 한다.
5. “이어서 조사해줘”: 실제 중단된 연구의 같은 ID/checkpoint로 재개해야 한다. 중단 시험을 위해 최초 연구를 임의 분할하지 않는다. 자연스러운 중단 또는 명시적 사용자 중지 사례에서 확인한다.
6. “HBM만 최신 자료로 확인해줘”: 요청 범위만 조사하고 이전 판단과 비교해야 한다. “전체를 오늘 기준으로 갱신해줘”는 새 기준일 campaign과 이전 보고서 비교로 연결해야 한다.
7. “기존 연구를 보존하면서 플러그인 업데이트를 준비해줘”: 신뢰 출처·호환성·백업을 확인한다. 실제 설치 갱신 뒤 새 대화에서 같은 프로젝트와 이력이 읽히는지 검증한다. 호스트 조작이 필요하면 그 단계만 명확히 안내한다.

저장 실패, 권한 없는 프로젝트, 여러 프로젝트, 미지원 schema, 표시 제한은 사용자 자료를 덮지 않고 필요한 조치로 안내해야 한다. DB 복구 시험은 사용자가 허용한 백업의 새 폴더에서 수행하고 기존 상태를 보존한다. 일정 예약·장기 보존은 별도 호스트 실증 항목이다.

결과에는 실행 환경, 설치/실행 버전, 각 요청의 실제 동작, 개입이 필요했던 지점, 산출물/상태 식별, 미확인 항목을 기록한다. 사용자가 위치·심화도·추세를 이해하고 다음 사용을 스스로 이어갈 수 있는지 확인한다.
